# 検体の要件 ── 測る前に満たしておくこと

この文書は ailine の設計でも使い方でもない。**検体（測定に使うデータ）を作る手順**を置く。
[docs/開発手法.md](開発手法.md) と同じ約束で書く:

- **原則は一行**で書き、**必ず「起きたこと」を添える**（原則だけ並べると一般論に見える）
- **実物の在り処を指す**。ここに書いたものは全部この repo で動いている
- ★ 一般論は書かない。**この機械の上で観測したこと**だけを書く

★ 検体は「データを用意すること」ではない。**測定器の一部**であり、
[治具と窒息点まで含めて仮説](開発手法.md)だ ── 検体が間違っていると、製品でなく
測定器が赤を出し、その赤を追って**正しい実装を壊す**。この repo では 1 日に 6 回起きた。

---

## 1. 検体そのもの（形）

### 1.1 ★★ 実務の密度で作る ── 疎な検体では、ある種の欠陥が**永久に**見つからない

**起きたこと（2026-09-13・需要③）**: 合成検体は過去の行が**疎**で、1 行に鍵（照合に使う列）が
1 つしか乗っていなかった。実務の仕訳は逆で、1 行に 取引先・摘要・補助科目・部門が**同時に**乗る。
Namakoo が実物の形式で用意した請求書 3 通から仕訳を起こして測ったら:

```
到達  合成検体 75%  →  実務の密度 30%
```

落ち方が想定と違った。鍵が当たらないのではなく、**広い鍵（取引先）の割れが、完全に一致して
いる狭い鍵（摘要）を道連れにして**全部空欄にしていた。

★ 決定的なのはここ ── **規則を直しても、合成 155 行の点数は 155/155 のまま 1 点も動かなかった。**
疎な検体では、割れた鍵と当たる鍵が同じ行に同居しないので、この欠陥は永久に出ない。

**要件**: 実物で**同じ行に同時に乗るもの**は、検体でも同じ行に乗せる。
1 項目 1 行に分解した検体は作りやすいが、**項目どうしの相互作用を測れない**。

実物: [bench/accounts/real_shape_case.py](../bench/accounts/real_shape_case.py)（実務の密度）／
[bench/accounts/specimens_accounts.py](../bench/accounts/specimens_accounts.py)（疎な合成）

### 1.2 ★ 汚さを写す ── 「引ける形」に寄せない

**起きたこと（2026-09-13）**: 合成検体の摘要は **17 行で 8 種**（『電話料金』が 5 行続く）。
実務の摘要は月・伝票番号・全角半角・手入力の揺れ・カード会社名が混ざる。
綺麗な検体で測った到達率は**上限**にしかならない。

**要件**: 検体の書き手に「**到達率が上がる方向の配慮を禁じる**」と明示的に指示する。
書き手は悪意なく「測りやすい形」を書く ── これは指示の不足であって、書き手の落ち度ではない。

実物で確かめた汚さの例（`real_shape_case.py`・形は 1 文字も変えていない）:
```
[注文#X992-1] ワイヤレスマウス MX-3     注文番号が毎回変わる（前月は #X880-2）
Ａ４コピー用紙（５００枚×５）            全角数字
ｵﾌｨｽﾁｪｱ / ﾀｸｼｰ乗車                    半角カナ
3月分 電話代（回線 0595-XX-XXXX） ／ 電話料金　4月分   同じ物の 2 通りの書き方・全角空白
ｲﾝﾀｰﾈｯﾄ接続料(◯◯ﾌﾟﾛｼﾞｪｸﾄ部門)        1 行に別の軸（部門）が密集
```

### 1.3 ★ 分布の床を先に決める ── 行数だけでは足りない

**起きたこと（2026-09-13）**: 採点器の床は `MIN_ROWS = 60` だけだった。
**全部が同じ区分の 60 行でも通る** ── その検体では「1 件でも確にする版」の変異を殺せない。

**要件**: 行数ではなく**分布**を事前登録し、機械で確かめる。この repo で登録したもの:

```
区分（確/単/割/無）それぞれ 8 行以上        ← 変異を殺すのに必要
測る対象のソフト 2 種以上                  ← 1 種では列解決の穴が出ない
複合仕訳の冊 1 冊以上                      ← 継続行に触らない契約を測る
貸方側だけに取引先が在る冊 1 冊以上          ← 片側だけ見る実装が通ってしまう
文字コード 2 種以上                        ← BOM 判定の穴
「怪しくない」冊 1 冊以上                   ← 偽の疑いを測る分母
```
実物: `distribution_floor()` in [bench/accounts/score_accounts.py](../bench/accounts/score_accounts.py)

### 1.4 ★ 出してはいけない行を入れる（負の被覆）

**起きたこと（2026-09-13・設計レビュー）**: 採点器は「答えが宣言した行」だけを回していた。
だから **余計に出した**（触ってはいけない行に値を書いた）が 1 件も鳴らなかった。

**要件**: 検体に「出してはいけない行」を**必ず混ぜ**、答えに列挙する。
この repo の形: `"触らない行": [行番号…]`（既に埋まっている行・複合仕訳の継続行・合計行）。
採点の見出しにも `★余計` `★混入` を立てる（`split` 側の先例: `bench/split_people/score_split.py`）。

### 1.5 ★ 断らせる形を入れる

道具が**断る**ことも契約なので、検体に断らせる形を入れる:
列が 0 本／2 本に当たる冊、鍵が 1 件も当たらない冊、今回と過去が同じファイル、
印の無いフォルダ、印が混ざったフォルダ。
★ 「全部空欄で exit 0」は**静かな成功**ですり抜ける ── 断りは必ず名指しで測る。

## 2. 答え（正解データ）

### 2.1 ★★ 答えは宣言から**機械的に導く**（手で書かない）

**要件**: 検体は「何を仕込んだか」の**宣言**として書き、答えはその宣言から関数で生成する。
手で書いた答えは、書き手が疲れた行から静かに狂う。

実物: [bench/accounts/specimens_accounts.py](../bench/accounts/specimens_accounts.py)（宣言）→
[bench/accounts/mk_accounts.py](../bench/accounts/mk_accounts.py)（実ファイルと答えを生成）

### 2.2 ★ 判定に要る項目を必須にする

**起きたこと（2026-09-13・設計レビュー）**: 「捏造（先例に無い値）」と「誤配（在る値の取り違え）」を
分けるには**先例に在る値の集合**が要る。初版はそれを「答えの科目」から作っていたので、
値を出さない区分（割・無）の科目が集合から漏れ、**誤配が捏造に化けていた**（★ の 2 本柱が入れ替わる）。

**要件**: 答えに必須項目を宣言し、採点器の入口で**存在を確かめて落とす**
（`REQUIRED` と `_check_answer()`・`score_accounts.py`）。

### 2.3 ★ 凍結の線 ── 「検体を見る前」と「見た後」

```
検体が 0 件のうち   採点器・契約・床は いくらでも直してよい
検体を見た後        答えに合わせて規則を直さない（それは測定でなく暗記）
```
★ この線は「凍結」の意味そのもの。凍結は**当てるため**でなく、**外れの向きを読むため**にある。

## 3. 作り手（独立性）

### 3.1 ★ 別の書き手に、読んではいけないものを名指しで渡す

検体の書き手が実装を読むと、**実装に通る検体**が出来る。逆も同じ。
この repo の指示の形（そのまま持っていける）:

```
★ 読んではいけない: src/ailine_core/<器官>.py, tests/ 配下すべて
   読むのは 2 つだけ: 設計文書（契約）と 採点器の docstring（出力の形）
```

### 3.2 ★★ 検体の欠けに合わせて**規則を広げない**

**起きたこと（2026-09-13）**: 検体が弥生の識別フラグ（一次資料では 4 桁の数字）を**空**にしていた。
実装者は読み手の受け入れを「4 桁」→「空か 4 桁以内」に**広げて**通した。
広げるのは「答えに合わせて規則を書く」のと同じ形 ── 直すのは**検体の側**。

**要件**: 実装が検体に不服を唱えたら、**一次資料に当たって検体を直す**。
広げた場合は陰性対照（広げた形を断る試験）を必ず置く。
★ これが拾えたのは、実装者が **ASSUMED に両案を書いて判断を仰いだ**から。
黙って広げられていたら、実物で効かない緩さが番人ごと入っていた。

### 3.3 ★ 報告は ASSUMED を**最初に**書かせる

「設計に無くて自分で決めたこと」に危険が溜まる。末尾に書かれると読み飛ばす。

## 4. 採点器（物差し）

### 4.1 ★★ 本体を import しない

同じ関数で作った分母は恒真になる。採点器は製品の器官（`ailine_core`）を import しない。
★ 例外は**出力の形式**（列名・シート名の登録簿）── それは規則ではなく取り決め。

### 4.2 ★ 対照 3 種と変異を `--self-test` に持たせる

```
陽性対照   答えをそのまま返す道具 → 全部「正」（★ ここが 100% でなければ採点器が壊れている）
陰性対照   黙る道具             → 「漏れ」だけが立ち、「誤配」は 0
変異       推測する道具          → 「誤配」や「格上げ」が立つ
```
★ **変異は「変えたつもり」では効かない** ── 未使用の変数を足しただけの変異が空振りして
「通ってしまった」と読めた（2026-09-13）。判定に至る経路を替え、当て先は**1 行で一意**にする。

実物: `self_test()` in `score_accounts.py` / `score_split.py` / `score_pdf.py`

### 4.3 ★ 正答率にしない ── 見出しを分ける

「85%」は、何を 15% 間違えたのかを隠す。この repo の見出しの例:

```
正 ／ ★誤配 ／ ★捏造 ／ ★余計 ／ 漏れ ／ 格上げ ／ 格下げ ／ 不親切 ／ 偽の疑い
```
★ 印（★）を付けた 3 つは**質が違う**（取り返しがつかない側）。1 つの率に混ぜない。
★ 1 冊 1 点のもの（偽の疑い）と 1 行 1 点のものを同じ列に並べるときは、
**分母に閉じないことを報告に書く**。

## 5. 公開の線

### 5.1 ★★ 実名は**機械に判定させる**（目で見て決めない）

**起きたこと（2026-09-12/13）**: 検体に実名の姓が入り、commit が止まった（2 度）。
2 度目は Namakoo 提供の PDF で、**実名の姓 2 箇所・実名の地名 4 箇所**を機械が当てた。

**要件**: 検体を repo に入れる前に `python ~/.tools/secretscan.py <file>` に掛ける。
当たったら**形は 1 文字も変えず名前だけ**差し替える（半角カナ・全角数字・空白は測定の値）。
★ 元ファイル（実物）は repo に入れない。差し替えたことと理由を検体の docstring に書く。

### 5.2 ★ 生成物と答えは commit しない

検体の**宣言と生成器**は commit し、生成された実ファイルと答えは `.gitignore` に入れる
（`bench/*/[a-z]*_books/`・`答え_*.json`）。公開 repo に答えが載ると、次に読む人が答えを見る。

### 5.3 ★ 第三者の雛形は repo に入れない

ベンダーの配布雛形・官公庁の様式は、読み取り専用で手元に置き、**repo には入れない**。
そこから起こした合成検体だけを入れる。

## 6. 数字が出た後の読み方

### 6.1 ★ 合成検体の数字は**上限**として読む

`README` にも看板にも「合成で N%」を単独で書かない。**分母の性質を隣に置く**。

### 6.2 ★★ 点数が**動かない**ときは「測れていない」かもしれない

規則を変えたのに点数が 1 点も動かなかったら、**その検体はその軸を測っていない**。
2026-09-13 の実例: 割れた鍵の扱いを変えても合成 155 行は 155/155 のまま動かなかった
（疎だから同居が起きない）。★ 差が出ない時はまず**測定器**を疑う。

### 6.3 ★ 100% は「易しい証拠」として読む

実務の密度の検体で 10/10 が出たとき、製品が強い証拠ではなく**検体の今回分が過去と同じ文面ばかり**
だった証拠として読み、そう書いた。次に効くのは「今回と違う摘要が多い月」のデータ。

★ 実例（2026-09-13）: 帳票の検体 87 冊・PDF 87 冊・束 51 冊・月末 125 冊で満点だったが、
**合計(税抜)と税込合計が同じ帯に同居する冊が 1 冊も無かった**。買い手役が自作の 5 枚で踏み、
税抜が「請求額(税込)」に入っていた（設計 §11）。被覆は**値**だけでなく**並び**（同じ帯にどの語が
同居し、どの順に出るか）にも要る ── 実務で普通の並びを、検体の書き手が「普通すぎて」書き落とす。

### 6.4 ★ 赤が出たら、製品を触る前に **1 件を手で解く**

2026-09-13 の 1 日で、赤の原因が**測定器の側**だったのが 6 回:
検分の名指しを読まず 11 件／文字セルだけ探して 12 件／項目名の別名を突き合わせず 13 件／
`return None` が 2 箇所あって変異が空振り／3 日前のログを現在と読む／物差しの語が広すぎて誤爆。
**どれも製品は正しかった。**
