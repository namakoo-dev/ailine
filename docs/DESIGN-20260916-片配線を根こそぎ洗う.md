# 片配線を根こそぎ洗う（2026-09-16）

Namakoo の指示:
> 片配線含む同様のケースを洗い出す必要がある。対症療法的に探すとコストも時間もかかるから根こそぎやったほうがいい

対症療法で 1 件ずつ追うのをやめ、**同じ形の欠陥がどこに在りうるか**を機械で数えてから潰す。
この文書は、何を数えたか・何が出たか・何を直したか・何を残したかを書く。

---

## §1 数え方 ── 「op の名簿」を全部見つける

ailine の判断の多くは「どの op がこの扱いを受けるか」の名簿で決まる。名簿が手書きで、
実装と食い違っていれば、そこが片配線になる。だから**名簿を機械で全部見つける**ところから入る。

番人（`tests/test_op_completeness.py`）は既に目録を持っていた。ところが走査条件が
**「dict リテラルで op 3 つ以上」**だけで、次のものが見えていなかった:

| 種別 | 見えなかった名簿 | op 数 |
|---|---|---|
| frozenset | `PLAN_CHAIN_CONSUMER_OPS` | 12 |
| frozenset | `_OPS_THAT_SKIP_NON_DATA_ROWS` | 3 |
| frozenset | `ROW_REDUCING_OPS` | 3 |
| tuple | `DEFAULT_SUGGESTIONS` | 3 |
| tuple | `PLAN_CHAIN_WARNING_OPS` | 2 |
| tuple | `KEEP_FOR_COLUMN_REQUEST` | 2 |
| dict | `OP_DECLARED_SHEET_NAME` | 2 |
| dict | `PLAN_CHAIN_UNNAMED_PRODUCERS` | 2 |
| dict | `MACHINE_DERIVED_ARGS` | 1 |

**名簿 23 本のうち 9 本が不可視**だった。見えない名簿は「部分なのは意図か、足し忘れか」を
誰にも問われない ── そこに片配線が溜まる。

→ 走査を `discover_op_rosters` に広げた（dict / set / frozenset / tuple / list、下限 1 件）。

## §2 出たもの① ── 合計行が実際に消えていた（`_OPS_THAT_SKIP_NON_DATA_ROWS`）

名簿は `{SORT, EXTRACT, SET_WHERE}` の 3 つ。実装から導くと **AGGREGATE も同じ扱い**だった
（`_codegen_aggregate` が `_skip_rows` を渡している）。名簿に無いので、

```
「合計行を除いて部署別に集計して」  → 先頭の行削除の段が落ちず、合計行が実際に消える
「合計行を除いて売上の多い順に並べ替えて」→ 段が落ちる（正しい）
「合計行を除いて9月の行を抜き出して」   → 段が落ちる（正しい）
```

同じ言い方なのに、**集計のときだけ台帳から合計行が消えていた**。

★ 見つけ方は「名簿」と「実装」を突き合わせただけ。名簿を目で読んでも気づけない。

**直し**: 名簿に `AGGREGATE` を足し、さらに番人
`test_skip_roster_equals_what_the_codegen_actually_does` で**実装から導いた集合と等号で縛った**。
数え方は 2 通りある（`_skip_rows` を渡す／`_sort_end_row` で末尾を切る）── 片方だけ見ると
SORT を見落とす。

## §3 出たもの② ── 関所が 1 op にしか置かれていなかった

朝に直した「条件つき書換を行追加にしない」関所は `ADD_ROW` **1 op** の中に置かれていた。
表の**構造を変える** op を実体から数えると **9 つ**在り、買い手の実文

> 納期が2026/09/30より後の行のチェック列に★を入れて

を 9 つ全部に通すと、**4 つが通った**:

```
止めた   ADD_ROW / DELETE_ROWS / LOOKUP_FILL / SPLIT_CELL / ADD_COLUMN
★ 通った APPEND_TOTAL / COMPUTE_COLUMN / DELETE_COLUMN / INSERT_ROWS
```

**直し**: 関所を op ごとに置かず、`verify_dsl_args` の**全 op が必ず通る 1 箇所**へ移した。
判定は `ailine_core/intent.py` に 1 つだけ置く（既存の作法）。

### 線の引き直し（ここが今日いちばん危なかった）

最初の一般化は「依頼文が列を名指ししていたら断る」だった。これを repo の
**正当な依頼 195 件**に通すと **56 件を誤って断った**:

```
備考という列を作って / 原価列を削除して / 数量に単価を掛けた列を作って …
```

列を作る・消す依頼はまさに「〜列を」と書く。**線は助詞でなく動詞の側に在った**。

```
断るのは:  書き込む動詞（入れて・付けて・書いて・入力して…）が在り、
           かつ  行き先の列（〜列に／〜列へ／〜列を）を名指し、または条件の語が在る
```

| | 事故の形 | 正当な依頼 |
|---|---|---|
| 助詞だけで断つ初版 | 6/6 | **誤り 56/195** |
| 動詞を必須にした版 | 6/6 | **誤り 0/195** |

★ 動詞を必須にしたので **op ごとの例外名簿が要らない** ──
「数量が100未満の行を削除して」（条件語あり・正当）は動詞が無く素通りする。
例外名簿を持つと、次に足す op で必ず同じ穴が開く。

★ 検体も op ごとに書かない。`tests/test_a_conditional_write_is_never_a_structural_change.py` が
**名簿から回して 9 op × 6 文 = 54 通り**を 1 本で縛る。変異 6 種すべてで赤くなることを確認した。

## §4 出たもの③ ── 表の終わりを Basic が 11 か所で自前に推測していた（**直した**）

買い手 2 体目の未処置の指摘「3 桁区切りが合計行で効かない」を追ったら、根はもっと広かった。

`src/ailine/helpers/AiLineHelpers.bas` の **10 本**が、それぞれ独立に
「左端の列が空になった行」で表の終わりを決めている:

```
AlignCenter / DedupRows / DrawTableBorders / ExtractRows / FormatThousands /
PivotSum / SortByColumn / SplitColumn / SummaryTable / VLookupFromTable
```

該当する op は **10/30**（AGGREGATE, CENTER_ALIGN, DEDUP, DRAW_BORDERS, EXTRACT,
LOOKUP_FILL, NUMBER_FORMAT, PIVOT, SORT, SPLIT_CELL）。

### 実機で確かめた（合計行の左端が空の受注台帳）

```
金額の列を3桁区切りにして   → × 適用されたが事後条件を満たさない
                             （列『金額』に桁区切り書式が付いていないセルがある・EXIT=1）
表全体を中央寄せにして      → × 表全体 に中央揃えでないセルがある（EXIT=1）
表に罫線を引いて            → × 使用範囲の一部に罫線が無い（EXIT=1）
```

事後条件は**正直**（やり損ねを見つけて ✓ を出さない）。ただし合計行を持つ台帳では
**書式の 3 op が丸ごと失敗する**。買い手は原本に何も適用できない。

### ★ 測り間違いを 1 件、自分で訂正する

最初にこの節を書いたとき、3 件とも「**✓ が出た**」と書いた。誤りだった。
`python -m ailine` は repo ではなく **site-packages の 0.1.1**（古い版）を走らせていて、
偽の ✓ はその古い版の挙動だった。`PYTHONPATH=src` を通して測り直したのが上の表。

★ 教訓は既に記憶に在ったもの（まず測定器を疑う）。**実機で測ったから正しい**ではない ──
  「どの実装を測ったか」まで確かめて初めて測ったことになる。
  以後この repo で実機を測るときは `PYTHONPATH=src` を必ず通す。

### 器官は在る

- `StyleBold` は Python から行範囲（row1/row2）を**受け取っている**。推測しない。
- `SortByColumnUpTo` は末尾の行を受け取る腕として既に在る。
- Python 側の走査は 2026-09-05 に「表の幅のどこかに値が在れば行」へ直してある
  （`_scan_last_row`）。**Python はもう正しい行数を知っている**。
- 1 列目が途中で空く形を名指しする器官 `detect_first_column_gap` も在り、
  並べ替えでは実機で正しく鳴った（「1列目が 3 行目で空いているため…」→ **⚠**）。

つまり **Python の数え方だけを直して、Basic 側 10 本を直していない**。
言語の境目で切れた片配線。

### 直した形（2026-09-16 午後・Namakoo の GO を受けて実施）

10 本それぞれに `〜UpTo` の腕を足すのは、同じ重複を 10 個から 20 個に増やすだけ。
**1 関数に畳んで呼び出し側に持たせない**（[[片配線]] の第三波で得た処方）:

```basic
Sub Run(oDoc As Object)
    Call SetTableExtent(5)        ' ★ Python が数えた表の終わり（0 なら従来の推測）
    Call FormatThousands(oDoc, 0, 3)
End Sub
```

各ヘルパの走査を `lastRow = TableLastRow(oSheet, headerRow)` の 1 本に置き換える。
- 渡された時はそれを使う（Python の正しい数）
- 渡されていない時だけ従来の推測に落ちる（後方互換）

★★ 実際にやったのは**もっと良い形**だった ── Python から数を渡す必要が無かった。
Basic 自身が Python と同じ規則（見出しの幅のどこかに値が在れば行）で数えればよく、
`SetTableExtent` は要らない。おかげで **生成する .bas は 1 文字も変わらず、
凍結した golden は 1 件も動かなかった**（GO をもらうとき「動く」と言ったが、動かずに済んだ）。

```basic
Function TableLastRow(oSheet As Object, headerRow As Integer) As Long
```

11 か所（うち 1 つは参照表を見る腕）をこの 1 本に差し替えた。

**直った側の実測**（実機・`PYTHONPATH=src`）:

```
金額の列を3桁区切りにして   × 3 行に適用  →  ✓ 4 行に適用
表全体を中央寄せにして      × 16 セル      →  ✓ 20 セル
表に罫線を引いて            × 16 セル      →  ✓ 20 セル
金額の多い順に並べ替えて    × 1 行だけ     →  ✓ 4 行を並べ替え
```

**壊していない側の実測**: 合計行のある表を並べ替えても、合計行は除外されて下に残る
（届く範囲を広げた代わりに除外が壊れていないか、そこまで見て完了とする）。
効果の行列 245 件は 242/断り3/失敗0 で許容（243±2）の中・壊していない 100%。
★ ただし行列の 11 表に「左端が空の行を持つ表」は 1 つも無い ──
  **この行列は直った分を測っていない**。直った側は
  `tests/test_a_blank_first_column_does_not_hide_the_rest.py` が実機で縛る
  （形の番人 3 本＋実機 5 本・変異 2 種で赤を確認）。

★ 「合計行を含めるべき op」と「除くべき op」は別問題のまま残る ──
  書式は**含める**、データ操作は `_skip_rows` / `_sort_end_row` で**除く**。
  今回そろえたのは「表がどこで終わるか」だけで、除外の側は既存の仕組みが受け持つ。

## §4b 出たもの④ ── 平均を頼むと合計が返り、✓ が出ていた（**直した**）

掃き出しで名簿 `op_axes.AXES` を見たとき、**合計しか計算しない 3 op のうち 1 つしか**
軸を宣言していなかった（APPEND_TOTAL だけ。AGGREGATE と PIVOT が無い）。

実機（作業ツリー）で確かめた:

```
部門ごとの平均金額を出して
  → 出力シート『集計』 見出し『合計 - 金額』
     青果 400（平均なら 200）／鮮魚 1200（平均なら 600）
  → ✓ 機械検証済み（EXIT=0）
```

★ **間違った答えに ✓** ── この道具でいちばん重い壊れ方。頼んだ人は気づけない。

### 器官は在った

`op_axes.py` は軸と「まだ扱えないもの」を宣言し、
「？ 平均はまだ扱えません（この道具の集約関数は 合計 だけです）」の文面まで持っていた。
ところが読まれるのは**語彙外の断り／もしかしての提案**の 3 経路だけで、
LLM が実在の op を返した**成功経路では一度も読まれていなかった**。

### 直し

- `AGGREGATE` / `PIVOT` に軸を宣言（APPEND_TOTAL と同じ軸・同じ穴）
- 判定を **`verify_dsl_args` の全 op が通る 1 箇所**へ（op ごとに書き分けない）。
  これで APPEND_TOTAL / COMPUTE_COLUMN / DEDUP の成功経路も同時に塞がった
- 誤爆は **0/31**（battery の軸を持つ op の検体）。「最大手」が『最大』を拾った 1 件は
  軸に `not_when`（実測で足す**閉じた**除外）を持たせて外した
- 実機の両方向で確認: 「平均」→ 断る（EXIT=3・通る書き方つき）／「集計」→ ✓

★ 件数の家系（件数/何件/回数/人数…）は軸に入れていない ── AGGREGATE 側に
「合計する列を依頼文が名指ししていれば通す」という**測って決めた逃げ道**が在り、
軸の判定はその形を持たない。畳むなら別途測ってからにする（理由つきで台帳に記載）。

## §5 常設の台帳（これが「根こそぎ」の本体）

1 回掃いても、次に op や名簿を足した人が同じ穴を開ける。だから**宣言を強制する番人**を足した。

`tests/test_op_completeness.py` の ④:

- 見つけた名簿は全部、`op_roster_coverage` に宣言を持つこと（新しい名簿を足した瞬間に赤）
- 「全域」と宣言したら、本当に全 op を持つこと
- 「部分」と宣言したら、**正直な理由**と**解除条件**を書くこと
- 「部分」が全 op を覆うようになったら、宣言を直させる（腐り防止）
- 宣言に在るのに実体が無くなったら赤（リネーム・削除の検出）

★ 免除簿と同じ作法（reason / unlock 必須）で揃えた。理由が分からないものは
  **「未調査」と書く** ── 作文しない。
