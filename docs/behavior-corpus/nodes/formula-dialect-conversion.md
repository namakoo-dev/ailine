# formula-dialect-conversion — LO 方言での式化と挿入耐性 SUM

**分類: う（LibreOffice の `setFormula` 方言・保存時変換という実装固有の挙動に結合）**

## 挙動

COMPUTE_COLUMN・APPEND_TOTAL は既定で **式（`setFormula`）を書く**（`--values` で
従来の値埋め込みに戻せる）。★ `setFormula` は **LibreOffice Basic/UNO 経由でのみ、
関数の多引数区切りに（Excel 方言のカンマ `,` でなく）セミコロン `;` を要求する方言**
になる。カンマで書くと `#VALUE!`/`#NAME?` になる（実測で真因特定）。ただし
**保存時に LibreOffice がファイル内部表現を Excel 方言（カンマ区切り）へ自動変換する**
ため、Python 側の事後条件チェッカーは保存後のファイルをカンマ区切り形として照合する
（codegen が書く形とチェッカーが読む形は文字として一致しない — これは方言変換込みの
正しい挙動であって、バグではない）。

単純な行内の二項演算（`=B2*C2` 型・COMPUTE_COLUMN の 2 列演算）は区切り記号もシート
参照も無いため、この方言の気遣いは不要（多引数関数・シート跨ぎ参照だけが方言の対象）。

APPEND_TOTAL の合計式は **挿入耐性のある SUM** で書く: `=SUM(D2:INDEX(D:D;ROW()-1))`
型。`INDEX(D:D;ROW()-1)` は「この式自身の 1 行上」を指すので、後でデータ行を 1 本
挿入しても SUM 範囲が自動で追従する（静的な `"D2:D5"` 型は追従しない）。

事後条件は**二層**で検証する: ①保存後の式文字列が期待形（カンマ区切りの
`=SUM(...INDEX(...))` 形）と一致するか ②`data_only=True` で読んだキャッシュ値が
演算結果（列合計×factor 等）と一致するか。両方合格して初めて pass にする（式だけ
合っていて未計算/値だけ合っていて式が無いケースの両方を見逃さない）。

## なぜ（一次資料つき）

- `#VALUE!` の真因特定はスパイク実験（`bench/formula_spike_work*`）で行った。原因は
  「LO 方言でセミコロンが必要」で、事前の仮説（型不一致等）は外れていた
- 挿入耐性式は `bench/formula_spike_work2` の実測ベンチで確立（静的範囲だと行挿入で
  範囲がずれる問題があった）
- COMPUTE_COLUMN の式化既定への切り替えは、LO 方言をコード生成テンプレで機械的に
  保証する設計判断（LLM に方言を意識させない）

- 出典: commit 586896a（`bench/formula_spike_RESULTS.md` — #VALUE! の真因特定）・
  commit 6973390（COMPUTE_COLUMN 既定を式に）・commit 03e3d11（APPEND_TOTAL の
  式+ラベル・二層事後条件）

## 検証挙動（GOLDEN 相当）

| 入力 | 期待 |
|---|---|
| COMPUTE_COLUMN（既定=式） | `=B2*C2` 型・シート参照/多引数が無いため方言変換の影響を受けない |
| APPEND_TOTAL（既定=式） | `INDEX` 区切りをセミコロンで codegen → 保存後カンマ形に変換 → 事後条件はカンマ形と照合 |
| データ行を 1 本挿入後の再検証 | SUM 範囲が自動追従（挿入耐性） |
| `--values` 指定 | 式でなく計算済みの値をそのまま書く（従来挙動） |
