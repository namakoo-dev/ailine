# apply-timeout — 適用タイムアウト（既定 ON）

**分類: う（プロセス管理・LibreOffice の応答性に結合）**

## 挙動

`run` のマクロ適用は既定 180 秒で打ち切る。超過時は子プロセスツリーを **PID 指定で** kill
し（名前一括 kill はしない）、「実行時エラー: マクロが N 秒で終了しない（無限ループの
可能性）」として修復ループに渡す — 正直な分類は実行時エラー（モデルが終了しないコードを
書いた）。`--timeout <秒>` で変更、`0` で無効（旧挙動）。多層防御として、basrun 自身の
timeout に加え外側の安全網（timeout+30 秒で basrun.py ごと kill）を持つ。

## なぜ

E 層測定（2026-08）で実測 2 回、モデルが終了しないループを生成し、`soffice.bin` が
CPU 546 秒・応答あり・終わらないまま全体をハングさせた。製品の既定は「放置しても
固まらない」でなければならない（冷間監査 2026-08-14 の製品バー判断も同旨）。

## ★ 既知の限界（2026-08-14 実機で確認・隠さない）

タイトな Basic ループで固まった LibreOffice は、kill 後の `stop_office()` が成功を
報告しても**即座には終了しない**ことがある（UNO の terminate() を処理できない）。
その間、出力ファイルがロックされ次の適用が「Device or resource busy」で失敗する。
**手動の `ailine stop` を挟むと回復する。**「次の適用で自動復旧」は常には成立しない —
自動復旧の強化（適用前のプロセス健全性チェック等）は将来課題。

- 出典: M1 実装時の実機検証記録（実誘発した `Do While True` で確認）・commit 688eab7

## 検証挙動（GOLDEN 相当）

| 入力 | 期待 |
|---|---|
| 終了しないマクロ + 既定 | 180 秒で実行時エラー化・修復ループへ・プロセス残存なし |
| `--timeout 0` | 打ち切りなし（旧挙動） |
| 制限より速い正常適用 | 発火しない（0.6 秒の適用に 1 秒制限で不発を実測済み） |
