# noop-guard-normalization — 適用前の正規化パス

**分類: う（LibreOffice の保存挙動に結合）**

## 挙動

`run` は測定（before スナップショット → マクロ適用 → after スナップショット → 9 軸差分）の
**前に**、コピーした出力ブックへ空のマクロ（`Sub Run(oDoc As Object)` のみ）を一度適用する。
この正規化パスは run 1 回につき 1 度だけ実行され、修復ループの各試行では繰り返さない。

## なぜ（一次資料つき）

LibreOffice は「LO で保存されたことがないブック」（openpyxl 等で作られたもの）を最初に
保存するとき、行高（時に列幅）を実体化する。正規化なしだと、この副作用が 9 軸の
「行高」に変化として計上され、**何もしないマクロでも「✓ 変化した」と成功表示になる**
（偽陽性）。`--inplace` 併用時は「何も起きていないのに原本を上書きして成功と報告」まで
起こり得た。

- 発見: 2026-08-14 冷間監査（初見ユーザー役）。最小再現 = 空 Sub + `--repair 0` →
  「✓ 適用され、文書が変化した。＊行高変更: Sheet」・openpyxl 照合で中身は完全一致
- 前史: 同じ現象は ailine-ts 移植（2026-08）が先に発見し、テストハーネス
  （fixture を LO 往復で正規化）として文書化していた。**原典の製品経路への還流が
  漏れていた** — 本ノードはその還流の記録（還流第二号）
- 修正 commit: ailine 4295532

## 設計上の不変条件（削ってはならない線）

- **9 軸は削らない。**「行高だけの変化を無視する」型の対処は、本物の行高変更を検出
  できなくする（軸を 1 本消すと no-op の穴が開き直すことは ailine-ts の
  axis-ablation テストが実証している）。対処は測定の正確化（正規化）側で行う
- 正規化のコスト = LibreOffice 往復 1 回（数秒）。正しさ優先で受け入れる

## 検証挙動（GOLDEN 相当）

| 入力 | 期待 |
|---|---|
| 空マクロ + fresh book | no-op 失敗（exit 1・修復ループへ） |
| 実変更マクロ（例: 降順ソート） + fresh book | ✓ 成功・変更点にセル値変更が見出しつきで並ぶ |
| 2 回目以降の適用（正規化済みブック） | 正規化パスの有無に関わらず判定一致 |
