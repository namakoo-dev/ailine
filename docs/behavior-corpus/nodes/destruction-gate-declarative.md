# destruction-gate-declarative — 破壊の関所と OP_WRITE_TARGET の宣言駆動

**分類: あ（設計原則そのもの — 「op ごとの if でなく宣言を読む」は言語非依存の骨格）**

## 挙動

原本へ直接反映する既定経路で、**既存データへの上書きが起きる操作**は
`--ask` 無指定でも確認を挟む（「破壊の関所」）。確認では上書きされる既存値の件数を
表示し、対話なら y/N、非対話なら **exit 7** で止める（`--overwrite` で明示的に
承知の上で続行できる・`ailine undo` で戻せる）。複合計画では段ごとにこの関所を通し、
原本（book）はどの段が拒否されても無傷のまま止まる（`out_book` はコピーで作業して
いるため）。

この関所が「どの op のどの引数が書き込み先か」を知る方法は、**`OP_WRITE_TARGET` と
いう宣言テーブルを読むこと**であって、op ごとの `if` 分岐ではない。各 op は
`(書き込み先の引数キー, シートを指す引数キー or None)` を宣言する（例:
`"COMPUTE_COLUMN": ("target", None)`・`"LOOKUP_FILL": ("target_col", "target_sheet")`・
書き込み先が既存列に及ばない op は `None`）。新しい op を追加する開発者はこの宣言に
必ず登録しなければならない — それを**機械的に強制するテスト**
（`test_op_write_target_declares_all_ops`）が「`OP_SCHEMA` の全 op が
`OP_WRITE_TARGET` に宣言を持つ」ことを検査する。同じ宣言は、新規列/新規シート作成の
ゴースト警告の中立化（意図した新設を誤警報しない判定）でも共有される（検出ロジックを
二重管理しない）。

## なぜ（一次資料つき）

初代実装（W10a）は関所を `COMPUTE_COLUMN` にしか適用しない事実上の白名簿
（`if op != "COMPUTE_COLUMN": return None` の 1 行）だった。W10c の実機査定
（$25）で、「単価表を見て単価を入れて」という自然な依頼に対し、`LOOKUP_FILL` が
対象列名を無関係な既存列（「数量」）へ解決し、**関所を素通りして無警告のまま
上書きした**事故が実測された。原因は「白名簿方式は op が増えるたびに人間が
if を書き足すことを要求する」構造そのもの — 忘れれば静かに脆弱になる。

宣言駆動への一般化はこの構造的欠陥を消す。★ これが「op を増やしても壊れない」
唯一の形だった、という判断がコミットメッセージに明示されている: 白名簿方式は
「足し忘れ」という人為ミスを許す余地が本質的にあり、宣言＋番人テストの組だけが
その余地を構造的に閉じる。

- 出典: commit 2b5afbe（W10a — 破壊の関所の初出・COMPUTE_COLUMN 限定）・
  commit ab34711（W10c — 「op ごとの if の白名簿だったのを OP_WRITE_TARGET 宣言の
  読み取りへ一般化。再発防止の本体は全 op が宣言を持つことを検査するテスト」・
  実機査定 $25 での事故再現）・commit 476f1ae（W10d — 新規列ゴースト警告の中立化も
  同じ宣言テーブルへ一般化 + 全 op を動的にループする番人テスト）

## 検証挙動（GOLDEN 相当）

| 入力 | 期待 |
|---|---|
| COMPUTE_COLUMN が既存列 target を指す | 上書き件数を表示して確認（非対話は exit 7） |
| LOOKUP_FILL が既存列へ解決される | 同じ関所が発火する（COMPUTE_COLUMN 専用だった旧実装では素通りしていた） |
| `OP_SCHEMA` に op を新規追加し `OP_WRITE_TARGET` への登録を忘れる | 番人テストが fail する（登録漏れの機械検出） |
| `--overwrite` 指定 | 関所を承知の上で素通し（`ailine undo` で戻せる） |
| 複合計画・1 段目で拒否 | 原本は無傷のまま計画全体が止まる |
