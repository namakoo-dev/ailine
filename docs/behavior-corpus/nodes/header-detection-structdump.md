# header-detection-structdump — 見出し行検出と StructDump

**分類: い（構造は渡るが、LibreOffice UNO 依存部分は実装ごとに再設計）**

## 挙動

`run` は正規化パス（LO 往復）に同乗させて **StructDump** を取る: シートごとの
「実使用範囲（`Cursor.gotoEndOfUsedArea(True)`）・図形/グラフ/DataPilot 個数」を
LibreOffice の目で機械読みする。追加の LO 起動は発生しない（正規化と StructDump は
同じ 1 往復に二役で乗る）。openpyxl の `ws.max_row` は書式だけ残った幽霊セルで
過大評価しうるため、実使用範囲だけは LO に聞く。一方、行ごとの書式的特徴（太字数等）や
結合範囲は、LO が保存し終えた同じファイルを openpyxl で読むだけで求まる（もう一度
LO を起動しない）。

見出し行の推定は StructDump の先頭 20 行（`STRUCT_HEADER_SCAN_ROWS`）を対象に、
「非空文字列セルが並び、行自体が全部文字列で、直下の行に文字列でない非空セル
（数値等）が混ざる」行を強い候補とする。強い候補が 0 個か 2 個以上（曖昧）なら
推測せず **CLARIFY** に退避する（`--header-row` で人に確認させる）。全列が文字列型
（数値/日付列が一つも無い表）は型混在の手がかりが構造的に発生しないため、スキャン
範囲内の非空行が例外なく全部文字列と確認できた場合に限り、最初の候補行を見出しと
みなすフォールバックを持つ。

推定した見出し行（`header_rows`）は **接地（describe_book_for_dsl）・codegen・
事後条件チェッカーの三層が同じ値を共有する**（相関故障の再発防止 — どこか一層だけ
違う行を見ていると、他の層が正しくても全体としては壊れる）。

## なぜ（一次資料つき）

- タイトル行つき帳票（A 検体）は物理 3 行目が実際の見出し、2 段結合見出し（D 検体）は
  子見出し行を採用しないと正しく動かない。旧実装（物理 1 行目固定）は D 検体で
  「静かに壊れる」（誤った行を見出しとして式・検証を組み立てるが、エラーにならない
  ため気づけない）実測を持っていた
- `gotoEndOfUsedArea(True)` は **実測で見つかった罠**: 引数 `False` だと端セルに潰れる
  （実測バグ）。`True`（拡張モード）でなければ実使用範囲を正しく取れない
- 子見出し行（多段見出しの下段）の先頭セルが空欄になるケースは、真上の行を遡って
  最初に見つかる非空値を引き継ぐ（親行フォールバック）。無いと打ち切り誤検知で
  列挙が 0 件になる（D 検体の商品名列で実測）
- 全列文字列型の表（氏名/部署/備考のみ等）は型混在という手がかりが一度も発生せず、
  素朴な実装では毎回 CLARIFY に落ちる（実測で発見・W10e で対処）

- 出典: commit 6973390（StructDump 本体・見出し行検出・三層共有）・commit d7200c3
  の隣接コメント（全列文字列型フォールバックは致命3(W10e)項目①として同時期に追加）

## 検証挙動（GOLDEN 相当）

| 入力 | 期待 |
|---|---|
| タイトル行つき帳票（A 検体）「金額で降順」 | 見出し 3 行目を検出して正動作 |
| 2 段結合見出し（D 検体）「7 月で降順」 | 子見出し行を検出（親行フォールバックで先頭空セルを埋める） |
| 見出し候補が曖昧（0 個/2 個以上） | 推測せず CLARIFY（`--header-row` の使い方まで誘導） |
| 全列が文字列型の表 | 型混在の手がかりが無いことを確認した上でのみ先頭候補行を確信とする |
