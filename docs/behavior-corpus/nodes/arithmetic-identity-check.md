# arithmetic-identity-check — 算術恒等の検算（二重計上・合計行の位置）

**分類: あ（設計原則そのもの — どの実装にもそのまま渡る）**

## 挙動

対象列の数値だけを見て、**自分より上の全数値の合計と一致する値を持つ行**を探す
（`ailine_core/sum_identity.py`）。辞書（「合計」「総計」「小計」）も書式も行の型も読まない
純粋な算術で、言語に依存しない。判定は「存在」ではなく**位置**で行う:

| 経路 | 見るもの | 鳴る条件 |
|---|---|---|
| `check_append_total` | 適用後の対象列（見出しの次の行から空欄まで） | **足し込んだ範囲の最終行**が恒等式を満たす（＝既にある合計をもう一度足し込んでいる）。並びの最後の数値行＝今書いた合計そのものは範囲から外す |
| `check_sort` | 適用**前**と適用後の対象列 | 前は最下行が恒等式を満たしていたのに、後では満たさない（＝合計行がデータとして並べ替えられた） |

★ `check_append_total` の「範囲の**最終行**だけ」は後から絞った線。最初は「最下行以外の
どこで一致しても鳴らす」にしていたが、同梱の `demo/sales.xlsx`（部門/金額 =
100,200,**300**,400,500,250）は 300 が開発部門のただの売上なのに 100+200 と一致し、
**README の quickstart が exit 1 で落ちた**。既にある合計はその塊の一番下に在り、
二重計上はそういう起き方をする ―― 範囲の真ん中で一致するのは偶然の側。
絞ってもなお語も書式も読まない（算術＋位置だけ）。実測（同梱ブック全数値列 139 本に
APPEND_TOTAL が走ったと仮定した掃き出し）: 発火 11 本（うち偽陽性 5）→ **6 本（偽陽性 0）**。

鳴ったら `fail` ―― `✓ 機械検証済み` を出さず、原本を上書きせず、
**どのセルのどの値か**を名指しする（例:「Sheet!B4 の 300 は B2:B3 の合計と一致します」）。
既存の「事後条件を満たさない」経路と同じ扱いで、新しい関所も新しい exit code も作らない。

## なぜ（一次資料つき）

`check_append_total` は**期待値を「合計式が生成したのと同じ範囲」から作っていた** ――
検算が被検算と同じ盲点を使う恒真式。実測: 既存の合計 300 を持つ表に合計を足すと 600 が
書かれ、「3 行の合計を検証」と言って `✓ 機械検証済み`・exit 0 で原本を上書きした。
並べ替えの事後条件にも同型があり、値のみの合計行つきの表を「金額で降順」に並べ替えると
合計行が 2 行目に来ても「5 行を検証（降順）」で通り、✓ が出て原本を上書きした。

この型は既に禁じられている（`empty-verification-ban.md`）。0 件を合格にしないのと同じ理由で、
**自分自身を範囲に含めた合計を「一致した」と言ってはならない**。

- 出典: 独立レビューが「最小の一歩」として指定。事前登録したバーは
  `tests/test_sum_identity.py` の docstring（T6/T7/T8b + F6〜F9）。
- F10（同梱の `demo/sales.xlsx` が exit 0 で通る）は**後から足した**。最初の実装は
  F6〜F9 が全部緑のまま README の quickstart で誤爆していた ―― 合成した表だけを
  凍結していて、**同梱の検体そのものを走らせるバーが1本も無かった**のが原因。

## 設計上の不変条件（削ってはならない線）

- **語を読まない。** `sum_identity.py` には docstring 以外の文字列リテラルが1つも無い
  （番人: `tests/test_sum_identity_unit.py::test_module_reads_no_words`）。語で見分ける実装は
  必ずどこかで文字列と突き合わせる ―― 突き合わせる相手が無ければ、語を読みようがない。
- **上に2つ以上の項が要る**（`MIN_TERMS`）。1 つだと「2 行目が 1 行目と等しい」だけで当たり、
  同じ金額が2つ並ぶ表で鳴りっぱなしになる。
- **合計 0 では立てない。** `0 == 0 + 0` は恒真で、空欄を 0 で埋めた列が丸ごと当たる。
- **最下行の合計は正常。** 合計は表の下に置くもの。異常なのは位置だけ。

## 既知の限界（算術だけでは越えられない線）

- **真陽性と偽陽性が同じ数の並びになる。** `[100, 200, 300]` の 300 が「既存の合計」なのか
  「ただのデータ」なのかは、算術だけでは原理的に区別できない（ラベルも書式も読まないから）。
  位置の条件（範囲の最終行）は**どちらが多いか**を突いているだけで、原理的な区別ではない。
- ★ **最終行に絞った代償は「取り逃がし」。** `本体 → 小計 → 本体 → 小計 → 合計` のように、
  既にある合計が範囲の最終行**でない**位置にある帳票は、二重に数えていても鳴らない。
  誤爆（見える失敗）を減らすために取り逃がし（見えない失敗）を増やす方へ倒した
  ―― この向きは意図的で、番人つき
  （`tests/test_sum_identity_unit.py::test_a_total_that_is_not_the_last_row_of_the_range_is_missed_on_purpose`）。
- ★ **累計列が一致を作りうること自体は本当。** 実在する累計（100/300/450/750）は当たらないが、
  増分が特定の並びのときに恒等式が成立する組み合わせは存在する（例: n=4 の 100/300/600/1000）。
  凍結している F7 の検体は影響を受けないが、「累計列は原理的に安全」ではない。
- **並べ替えは、並べ替えた列しか見ない。** 別の列を並べ替えたせいで合計行が動いても鳴らない。
- **`source_book`（適用前のコピー）が無い経路では並べ替えの検査は黙る。** before が無ければ
  位置の変化は測れない ―― 測れないことを合格側にも不合格側にも寄せない。
- **式のキャッシュ値が無い行は項に入らない。** LibreOffice を通していないブックでは、
  範囲の中の既存の合計を見落とすことがある。

## 検証挙動（GOLDEN 相当）

| 入力 | 期待 |
|---|---|
| 既存の合計（値）を持つ表に合計を追加 | fail・exit 1・原本無傷・該当セルを名指し |
| 既存の合計（式）を持つ表に合計を追加 | fail・既存の合計行を名指し（「式が期待形でない」の誤診断を出さない） |
| 値のみの合計行つき表を対象列で並べ替え | fail・✓ を出さない・原本を上書きしない |
| データ行が 2 行以下 | 沈黙 |
| 累計列（各行が上を足し込む列） | 沈黙 |
| factor 1.1（税込み等）の正常系 | 沈黙 |
| 空行で区切られた 2 つの塊 | 上の塊しか読まない（誤爆しない） |
| 同梱の `demo/sales.xlsx` に合計を追加（README の quickstart） | 沈黙・exit 0・✓（100+200==300 は偶然） |
| 範囲の途中に合計がある帳票（本体→小計→本体→小計→合計） | ★ 鳴らない（既知の取り逃がし） |
