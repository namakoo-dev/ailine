# なぜこの形か ── 選ばなかった道と、その理由

> この文書は「何ができるか」ではなく、**何をしないと決めたか**を書きます。
> README が「作った道」の地図なら、こちらは**その外側の境界**です。
>
> ★ 2026-09-01 の技術面談で、聞かれて即答できなかった 4 つがそのまま元になっています。
> 　答えはすべて repo の中に在りましたが、**言葉になっていませんでした。**
> 　次に誰かが同じことを聞いたとき、人が説明しなくても済むように置いておきます。

## 1. なぜ CSV ではなく `.xlsx` を作業場にするのか

### CSV は既に入口にも出口にもある

```bash
ailine csv          # CSV を検疫して隣に xlsx を作る（0 落ち等を守って壊さず開ける形に）
ailine export-csv   # xlsx のシートを CSV へ書き出す（検疫の逆方向）
ailine export-pdf   # PDF へ書き出す（出した PDF を読み戻して確かめる）
```

`.xlsx` は唯一の形式ではなく、**作業する場所**として選んでいます。
なお CSV は素通しにしていません ── **検疫**を挟みます（先頭ゼロの品番が数値になる、
日付に化ける）。CSV は素朴に読むと壊れる形式です。

### 作業場を CSV にすると、式とシートが往復で消える

`demo/1_請求_2026年8月.xlsx` の実体:

```
F2:F7  =E2*1.1                       税込金額
E8     =SUM(E2:INDEX(E:E,ROW()-1))   合計
シート  8月請求 / 雛形 / 雛形_英文
```

CSV に落とすと、この式は**ただの数字**になります。戻したときには式が消えている。
翌月そのファイルに 1 行足した人は、**合計が増えないことに気づきません。**
シートも 3 枚 → 1 枚になります（CSV に「複数シート」という概念がない）。

書式・条件付き書式・図形・ピボット・VBA も同じです。だから適用は openpyxl ではなく
**LibreOffice を実際に開いて保存する**形にしています ── 触っていない要素を残すためです。

### 一番効く理由: CSV だと検算が弱くなる

この道具の `⚠` で価値が高いのは**参照のズレ**です。行を入れ替えた・列を足したときに

```
=SUM(E2:INDEX(E:E,ROW()-1))
```

が**何を指しているか**を追い、指す先がずれたら言います
（`src/ailine_core/cellmap.py` の `formulas_after` / `reference_drift_note`）。

**CSV には式が無いので、この検算は原理的に存在できません。**

> CSV にすると「便利になる」のではなく、**壊れたことに気づけなくなる。**

### CSV のほうが正しい場面

| こういう仕事 | 使うべきもの |
|---|---|
| 機械 → 機械。人が開かない中間データ | **CSV + pandas。この道具は要らない** |
| 見た目も式も要らない純粋な変換 | 同上 |
| 人が開く。式と体裁が成果物の一部 | `.xlsx`（この道具の射程） |

## 2. なぜ SQL / DB ではないのか

### データを操る道具としては、DB のほうが上

**集合演算・トランザクション・同時実行・規模** ── この 4 つは今も DB のほうが上です。
そこを争う気はありません。

よく続けて書かれるのが「**スキーマが宣言されているから検証も要らない**」ですが、
ここは**半分しか正しくありません**。スキーマが守るのは **宣言された不変量だけ**です。

### だがその前提は「データがもう DB に在る」

想定しているのは中小企業・個人事業の事務です。**データは PC の中の `.xlsx` に在ります。**
「DB のほうが適している」は、実際にはこういう提案になります:

```
① スキーマを設計する  ② 過去ぶんを移行する  ③ 入力画面を作る
④ そして最後に、請求書を Excel か PDF で出す仕組みを作る
```

**④ が残ります。**成果物はテーブルではなく**その書類**だからです。
1 冊の Excel を直したいだけなのに、道具が 3 つ増えます。

### 核心: スキーマが無いから難しい

**SQL なら検証は易しい。だからそこは解くべき問題ではありませんでした。**

表計算にはスキーマがありません。

```
どのセルにも何でも入る
合計行は、見た目がデータ行と同じ
「単価」はただの数値で、金額との関係はどこにも書かれていない
列が動く。行が増える。式が参照ごとずれる
```

やったのは、**構造の無い格子から、検証できるだけの構造を復元すること**です。

例: `金額 ＝ 件数 × 単価` はどこにも宣言されていません。
`src/ailine_core/row_identity.py` は**数だけ**を見て、

```
操作の前、全データ行で成り立つ列どうしの等式を探す → 5列 ＝ 3列 × 4列
操作の後、まだ成り立つか見る                       → 崩れた → ⚠
```

`金額` が computed column として**宣言されていれば**、DB ならこれは 1 行です。
★ **問題は、現場の表でそう宣言されていないこと**です。そして同じことは DB でも起きます。

### 実測: DB でも同じ穴が開く

`金額` を「ただの数値列」として持つ、ごく普通のテーブルで確かめました
（`bench/sql_invariant_demo.py` ── SQLite だけで走るので、そのまま試せます）。

```
CREATE TABLE 明細(
  取引先 TEXT NOT NULL,
  件数 INTEGER NOT NULL CHECK(件数 > 0),
  単価 INTEGER NOT NULL CHECK(単価 > 0),
  金額 INTEGER NOT NULL CHECK(金額 > 0))    ← 金額はただの数値列
```

依頼は同じ「丸和物流とみどり建設の単価を入れ替えて」。結果:

```
SQL が言うこと : 「2 行更新しました」 ── それだけ
制約チェック   : 全部通っている（件数>0・単価>0・金額>0）
実際の表       : 丸和物流  12 × 7200 = 86,400 なのに 金額 57,600
                 みどり建設  8 × 4800 = 38,400 なのに 金額 57,600
```

**CHECK 制約を 1 つも破らずに、表が矛盾しました。**
DB は「不正な値」を止めますが、「**宣言されていない不変量が崩れたこと**」は誰も見ていません。

同じ表を `src/ailine_core/row_identity.py` に通すと:

```
操作前に見つけた等式: (金額, ×, 件数, 単価)    ← 語も見出しも読まず、数だけから復元
操作後              : 崩れた
→ 『金額』＝『件数』×『単価』が全行で成り立っていましたが、成り立たなくなりました
```

★ これは「SQL より上」という話ではありません。**「SQL にも同じ層が要る」**という話です。
`.xlsx` はスキーマが 1 つも無いので、この層を**一番厳しい条件**で作ることになりました。
できたものは表計算に固有ではなく、**宣言されていない不変量を持つ表なら、どこでも同じです。**

### SQL にしても LLM の問題は消えない

text-to-SQL は**まったく同じ壊れ方**をします ── もっともらしいが違うクエリ。
しかも被害は大きい（`WHERE` の無い `UPDATE` は一撃で表を潰す）。

だから設計はそのまま移せます:

```
LLM に直接 SQL を書かせない → 何をするかを宣言させる
宣言を実体（スキーマ・実データ）と突き合わせてから実行する
実行後に読み直して、宣言どおりかを確かめる
確かめられなければ ✓ を出さない
```

`.xlsx` は、この形を**一番厳しい条件**で試すための題材です ──
型も制約もログもトランザクションも無い場所で成り立つなら、DB では楽になります。

### DB のほうが正しい場面

| こうなら | 使うべき |
|---|---|
| データが既に DB に在る／複数人が同時に書く／百万行 | **SQL。この道具は要らない** |
| 毎月同じパイプラインを回す | 同上（そもそも自然言語が要らない） |
| 手元の 1 冊を直す・成果物がその文書 | この道具 |

★ 規模も同時実行も**測っていません。** `ailine run` は同時に 1 本しか走りません。
　そこは狙っていません。

## 3. 帳票以外でも使えるのか（射程）

### 操作は分野に依存していない

登録した 29 操作に**業務の言葉は 1 つも入っていません**（`ailine ops` が正）。
並べ替え・計算列・集計・転記・行追加・列削除・条件つき書換・抽出・重複除去 ……
見ているのは表の形だけです。

### それを測ってある

効果で測る検体（`bench/basic_ops_matrix.py`）は、**わざと関係のない 3 分野**で組んでいます。

```
在庫   品名 ／ 棚 ／ 数量 ／ 備考
名簿   氏名 ／ 所属 ／ 内線 ／ メモ      ← 4 列目はわざと見慣れない語にした
献立   料理 ／ 主材料 ／ 分量 ／ 備考
```

```
表 7 種 × 基本操作 21 種 × 言い回しの揺れ = <!-- MATRIX_CASES -->230<!-- /MATRIX_CASES --> 件 → 意図どおり <!-- MATRIX -->221/230 = 96.1%<!-- /MATRIX -->・壊した 2（未解決 ── 落とさずに分母に残している）
```

**帳票は 1 件も入っていません。**判定は操作名ではなく**出来上がったファイル**で見ます。

### ただし「白紙から作る」はしない

「売上表を作って」で表を生み出すことはしません。
やるのは、**既にある表から別の表や書類を組み立てる**ことです
（6 行のデータ → 請求書 5 枚 = `REPORT_PER_ROW`）。

理由は **LLM に値を決めさせないため**です。

> 値も名前も、依頼文か実表からそのまま取る（A' 原則）。
> LLM が作った数字が表に入った瞬間、「読み戻して確かめた」に意味が無くなります。
> **元が無いものは、照合する相手がありません。**
> 空欄のほうが、それらしい誤値より安い。

### 弱いのは語彙の広さ ── そしてそれは測って決めた

29 操作に無い依頼は断ります（「ガントチャートを作って」等）。
広げる実験はしました:

```
操作の一覧に 5 つ足す
  → モデルに届く率   79.2% → 89.6%   （上がった）
  → 完遂率           98.9% → 82.8%   （下がった）
  → 壊した件数         0 →  9        （増えた）
→ 戻した
```

**広げると届きますが、機械が持っていた確実な経路をモデルが奪います。**

## 4. 機械検証は、どこまでの情報を持っているのか

### 単価を 2 つ入れ替えた場合（`_check_swap_cells`）

```
① 座標を決める   依頼文 ＋ 実表の見出し・行名だけで解く → [(2,4), (7,4)]
                 ★ LLM は座標を決めない
② 値を取る       実ファイルを開いて 4800 と 7200 を読む
                 ★ LLM に値を作らせない
③ Basic を組む   互いの値を書く（テンプレート・LLM ではない）
④ 適用           LibreOffice
⑤ 事後条件       適用後のファイルと適用前のファイルを **両方開き直して** 突き合わせる
```

⑤ で見るのは 3 つです。

```
① 宣言した 2 セルが、互いの値になっているか
② 変わったセルが ちょうど 2 個 か     ← 使用範囲を丸ごと読んで差分を取る
③ その 2 個の座標が、宣言と一致するか
```

**② が要です。**「どこが変わったか」を出力からではなく、
**適用前と適用後の全セルの差**から数えます。だから行を丸ごと動かせば 16 セル変わり、

```
2 セルのはずが 16 セル変わっています（…） ── 行や列ごと動かした疑いがあります
```

で落ちます。**これは 2026-08-31 に実際に起きた事故で、この検算を足して塞ぎました。**

適用前のファイルが無い回は ① だけの `warn` に落ち、**`✓` は出ません。**

### 持っていないもの（正直に）

- **「正しい 2 セルだったか」は証明していません。**証明しているのは
  「**宣言した** 2 セルだけが入れ替わった」です。座標の解釈そのものが間違っていれば通ります。
  三項（依頼・宣言・実体）のうち機械が突き合わせられるのは**宣言と実体だけ** ──
  だから書く前に「こう読みました」を人に見せます。そこは人の担当です。
- **式のセルは文字で比べていません**（②③ と読み戻しで見ます）。
- **等式は「全行で成り立つ」ものしか拾いません。**1 行でも例外があれば等式と見なさず、
  3 行未満の表では見ません（偶然の一致を拾わないため）。
- **列が動いた回は、等式を比べません。**等式を列の位置で持っているので、
  並びが変われば同じ等式が別の組に見え、「崩れた」と誤検出します
  （2026-09-01 に実測して塞いだ・14 件目）。

## まとめ ── この道具が向いていない仕事

正直に書いておきます。**下に当てはまるなら、別の道具のほうが速くて確実です。**

| こういう仕事 | 使うべきもの |
|---|---|
| 人が開かない中間データの変換 | CSV + pandas |
| データが既に DB に在る／同時に何人も書く／百万行 | SQL |
| 毎月まったく同じ処理を回す | スクリプト（自然言語が要らない） |
| 白紙から中身のある表を作ってほしい | 別の道具（この道具は値を発明しない） |
| 語彙に無い操作（ガントチャート等） | 別の道具（生成に入らず断ります） |

**向いているのは 1 つだけです** ──
**人が開く 1 冊の Excel を、日本語で直したい。ただし黙って壊されたら困る。**
