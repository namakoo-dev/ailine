# 盲検の合格線（2026-09-17 凍結・Namakoo 決裁）

★★ **これは直す前に置く線である。**後から自分に都合よく動かさない。
  1〜3 体目の結果や、今日直した内容から**逆算していない**（凍結の作法・棚の
  「事前登録: 反証の線を数値で先に決める」）。

## なぜ線が要るか

3 体回したが、どれも「所見が N 件出た」で終わっていて**合否を出していなかった**。
線が無いまま回すと、直した後に「今回は良かった」と言いたくなる ── それは 2026-09-17 に
1 日で 6 回踏んだ「測定器の側が壊れる」形と同じ。

★ Namakoo の言葉が定義そのものになった:
**「どんな指示に対しても到達するか、適切な断りを出すこと」**

★ これは症状の列挙ではなく**契約**である。列挙は必ず漏れる（新しい壊れ方が出るたびに
条件を足すことになる）。この形は閉じている ── **結果は 2 つだけ。それ以外は全部不合格。**

## ★★ 目的 ── 断りは成果ではない（2026-09-17 夜に追記）

★ **追記の理由を先に書く**（凍結した物を動かす作法）: 初版は「到達」と「適切な断り」を
  **同格の 2 つの出口**として並べていた。その形だと**全部を丁寧に断れば合格になる**ため、
  目的が「断り方の整備」にすり替わる余地があった。条件（9 条）は 1 つも変えない。
  欠けていた**目的**だけを足す。

★ Namakoo:「**断りは許されるが、ベストは断らずに完遂することだ。俺たちがやるのは
  適切な断りをまとめることじゃない。断りは仕方なく断るにすぎない**」。

- **合格は床であって目標ではない。**目標は**到達が増え、断りが減る**こと
- 回ごとに **到達 a 件 / 断り b 件** を記録する。**合格していても断りが増えたら退行**として扱う
- `tests/refusal_register.json` は維持する目録ではなく **縮める在庫**。`unlock` の欄が本体

★★ ただし**到達を増やす道は「当てて出す」ではない**。確信度を下げれば断りは減るが、
  それは「見えずに間違う」側へ倒れる ── この文書がいちばん重く扱う失敗そのもの。
  到達を増やす道は 3 つしかない（断りの台帳の分類がそのまま対応する）:

| 分類 | 件数 | 到達へ変える手 |
|---|---|---|
| vocab | 5 | **能力を足す**（筆頭: フォルダ × 抽出以外＝2 冊をまたいだ転記） |
| ambiguous | 10 | **聞けば決まるものを関所へ動かす**（2026-09-17 に削除をこれで動かした） |
| precondition | 5 | **道具が自分で前提を満たす**（式のままの列 ── LibreOffice を持つのに人に開かせている） |
| dangerous | 3 | 動かさない。ここだけは断りのままが正しい |

★ 断り 23 件のうち **20 件は原理的に到達側へ動かせる**。断りの数は、
  **まだ作れていないものの数**でしかない。

## 合格の定義

**その回に打たれた全ての指示が、次のどちらかに収まること。**

### ① 到達（4 つ全部を満たす）

| | 条件 | 出所（実際に破れた回） |
|---|---|---|
| 1 | 中身が正しい（`✓` が嘘でない） | 3 体目①（照合が単価を足して +5200）／1 体目①（並べ替えが明細に掛かり ✓） |
| 2 | 頼んでいないものを変えない | 2 体目（「印を付けて」が行追加に化け、台帳に架空の行） |
| 3 | 成果が消えない | 3 体目⑤（`--copy` の 2 回目が 1 回目を黙って置き換え） |
| 4 | 戻せる | undo（3 体目が 3 世代 md5 一致を確認・現状は満たしている） |

### ② 適切な断り（5 つ全部を満たす）

| | 条件 | 出所（実際に破れた回） |
|---|---|---|
| 1 | 本当の理由を言う | 3 体目③④（式のままで計算結果が無いことを言わず「決まりません」だけ） |
| 2 | **文言が正確** | 2026-08-26（ailine 自身が作った冊を「人のファイル」と断定）／1 体目⑦（本当の理由は列同士の比較なのに「一覧に無い」）／3 体目③④（既にそう書いている人に「例:『品目をキーに』と書け」＝実行不能な助言）／3 体目⑥（読んだだけの冊に「そのあと変更されています」・未再現） |
| 3 | 通る道を示し、**その道が通ることを機械で歩いて確かめてある** | `python scripts/walk_refusals.py` の実測（2026-09-20）: walked 14 / no_path 1 / 未調査 2 / by_design 7 / **path_fails 0**（計 24）── 初回（2026-09-19）は walked 11 / vague 3 で、その 3 件を直した |
| 4 | 終了コードが「成功」でない | 2026-09-15（全段が未対応なのに exit 0 ＋ `"ok": true`） |
| 5 | 1 バイトも書かない | 3 体目⑥（断った run が `.out` を残し、次の run を止める） |

★★ 3 の「歩いて確かめる」を足した理由（2026-09-19 追記・凍結した物を動かす作法どおり
  **理由を先に書く**。9 条の構造は 1 つも変えない ── 3 条目の**測り方**だけを足す）:

  ★ Namakoo:「到達率を極大にするのは大事だけど、**漏らした依頼を適切に判断しユーザを
    正解に導いてやること**までやるから」。ところが機械が見ていたのは
    escape/example（逃げ道の語や例が**文言に在るか**）だけで、**その道が通るか**は
    誰も確かめていなかった ── この repo が何度も踏んだ「宣言 vs 実体」の隙間。
  ★ 導通の盤（`scripts/walk_refusals.py`）が出す verdict は 9 つ ──
    `walked`（歩いて着いた）／`by_design`（意図した行き止まり）／`vague`（理由が粗い）／
    `no_path`（機能が無い）／`path_fails`（★ 通らない道を示した）／
    `未調査`（この器では歩けない）／`未記入`（歩き方を書いていない）／
    `引き金が引けない`（検体が古い）／`歩けなかった`（★ 機械が塞がっていた）。
  ★★ `歩けなかった` を足した理由（2026-09-20）: 盤は道を歩く時に実機を使うので、
    別の走行が実行ロックを握っていると製品が exit 6「別の ailine が実行中です」を返す。
    旧版はこれを `path_fails`（通らない道）と読んでいた ── **測れなかったのに
    「通らない」と主張していた**形。実測でいちどに 10 件が偽の赤になった。
    ★ 2 回歩く形（一度きりの失敗を赤にしない）では防げない ── ロックは数分握られる。
    ★ ロックの**ファイルを見る**形は使えない（conftest が AILINE_HOME をテストごとに
      差し替えるのでテストからは見えない・実装して確かめた）。読むのは**製品自身の
      終了コード**にした ── 走らせ方（pytest / CLI）によらず同じ答えになる。
  ★ 盤が、断りを出させ → 示された道を歩き →
    着いたかを判定する。verdict は台帳に書かない（歩いた結果から決める）。

★★ 導通率は**合格条件にしない**（2026-09-19・実測で決めた）:

  3 体分の所見 26 件を「買い手に何が起きたか」で仕分けた:

  ```
  嘘の到達      9 件 (34.6%)   やったと言って、やっていない／違うことをした
  言葉          6 件 (23.1%)   開発者語・README 700 行
  ★ 導通        5 件 (19.2%)   断られて、次に何をすればいいか分からない
  到達できない   4 件 (15.4%)
  嘘の断り      2 件 ( 7.7%)
  ```

  ★★ そして買い手が**導入を断る理由として名指しした 5 件は、すべて「嘘の到達」**だった
    （4 体目①「作業記録が嘘をつくのは致命的。この 1 点だけで所長に導入を提案できません」／
     4 体目②「そのままでは紙より悪い。この機能は無いのと同じ」／4 体目④「一番埋めたい列が
     一番無防備」／3 体目①「照合の差額が単価を足していた」／1 体目①「✓ が嘘だった」）。
    **導通は 1 件も入っていない。**

  ★ 導通率を条件に足しても**捕まえる欠陥は 1 件も増えず**、増えるのは「率が閾値を割ったから
    不合格」という、買い手が一度も不満を言っていない理由での不合格だけ。しかも閾値の根拠が
    無い（いま 11/17 ＝ 65% だが、65% が買い手にとって良いか悪いかを示すデータが 1 件も無い）。
  ★ だから導通は「**断りが嘘でないことの担保**」として持つ。本質は **path_fails が 0**
    ＝ 通らない道を示していないこと。`walked` の件数は**在庫の目盛り**として台帳が持つ。

★★ 2 の「正確」は測れる語にする ── **道具が観測していないことを主張しない**:
  - 見たこと（記録が無い／値が数えられない／語が辞書に無い）は言ってよい
  - そこからの**解釈**（誰の物か・なぜそうなったか）を**断定しない**
  - **助言は、その回の入力に対して実際に通ること**
  ★ この線は 2026-08-26 に既にコードへ書かれていた（「見たものと、その解釈を分ける」）。
    他の断りに配線されていないだけ ── いつもの片配線。

## 不合格の中の別格 ── 取り返しの非対称

★★ Namakoo:「ユーザは恥をかくだけで済むが、**俺たちに対する不信感は二度とぬぐえない**。
返金要求されてもおかしくない」。

重さは**買い手が受ける損**ではなく**こちらが失う信用**で測る。

| 種類 | 買い手の損 | こちらの損 | 例 |
|---|---|---|---|
| **見えて壊れる** | 困る・待つ | ほぼ無い（「まだできないのか」で終わる） | 語彙が無い・断られる・詰まる |
| **見えずに間違う** | 気づかず外へ持っていく | **その後に出す正しい数字も全部疑われる** | ✓ が嘘・黙って消える・断りの文言が偽 |

★ 同じ不合格でも、次に何をするかが変わる。**「嘘をつく側」は別格**として記録する。
★ 実際 3 体目の買い手は、機能の不足には買い切り 1 万円を出すと言いながら、
  間違った数字 1 つに対しては「仕入先に文句を言いに行ったら恥をかく」と言った。
  **足りないことは許されるが、嘘をつくことは許されない。**
★ 棚の線とも一致: 「順序は取り返しで決める ── 金に近い順に並べない。静かに壊れるものが先」。

## 分母 ── 何を「全ての指示」と呼ぶか

★★ その回に買い手が打った指示だけを分母にすると、**回ごとに分母が違って運で受かる**。

だから:

```
盲検 N 体目を回す
  → その回の history（ailine 自身が全 run を記録している）から
     打たれた指示を**全量**抜き出して凍結する（通ったものも、断られたものも）
  → 合否は「その回の全指示が ① か ② に収まるか」
  → 次の回の合格条件に、**過去の回の指示も含める**（退行の検出）
```

★ 現状の穴（2026-09-17 時点の実測）: 1・2 体目は設計文書に**事故になった指示しか**
残っていない。**通った指示は記録されていない** ── 退行の検出が丸ごと抜けている。

## ★★ 訂正（2026-09-18・実測して分かった）

初版はここに「`ailine history` が `task` を全件持っている」と書いた。**間違いだった。**

| 打ったもの | history に残るか |
|---|---|
| `run`（DSL / 計画 / 照合）／`csv` 変換／`export-csv` | ○ 通った回も断られた回も |
| `ops` / `doctor` / `history` / `scan` / `verify` / `--help` / 引数なし | **× 1 行も残らない** |

★ 買い手 3 体目は README → `doctor` → `ops` → `--help` → `scan` と辿ってから `run` に入った。
  **入口で詰まった話が丸ごと分母から落ちる** ── 1 体目の「PDF は案内どおり打つと必ず止まる」が
  まさにその形で、いちばん買い手を失う種類の欠陥が測れない。
★ さらに `--copy` / `--dry` / `--out` などの**引数も残らず**、冊の「その時の中身」も残らない
  ので、そのままでは流し直せない。

**だから分母は history では閉じない。**2026-09-18 に道具を作った（`scripts/blind_run.py`）:

- `AILINE_TRACE=<path>` … 盲検の回だけ**打った全コマンド**（argv）を控える。既定は無効。
  ★ history には足さない ── history は買い手の**月次の証跡**で、`doctor` が並ぶと雑音になる
- `AILINE_HOME=<回のフォルダ>` … その回の履歴だけを 1 ファイルに隔離（実測で確認）
- `freeze / replay / floor / sheet` … 凍らせる／並びごと流し直す／**揺れの床**を測る／
  機械で決まる 5 条だけの採点表

★★ **揺れの床**を測る部品を足した理由: 一段目は LLM で、同じ入力に同じ答えが返る保証が無い。
  床を知らずに差を読むと「直したせいか、モデルの気分か」を分けられない ──
  2026-09-18 に「自分の検体が作った幻」を 2 件追いかけたのと同じ失敗を、次は 1 回ぶん
  ぜんぶの規模でやることになる。

★ 採点で**機械が決めるのは 9 条のうち 5 つだけ**（成果が消えない／戻せる／通る道を示す／
  終了コードが成功でない／1 バイトも書かない）。残り 4 つ（中身が正しい／頼んでいないものを
  変えない／本当の理由を言う／文言が正確）は**人が読む**。その人も盲検にする。
  ★ 混ぜない ── 混ぜると「機械が合格と言った」が独り歩きする。

## この線で測らないもの（記録はするが不合格にしない）

語彙の不足／言い回しの硬さ／README の長さ／値段／勧めるかどうか／速度。
★ これらは「**まだ無い**」であって「**嘘をつく**」ではない。混ぜると線がぼやける。

## 4 体目を回す前にやること

1. history から指示を切り出して凍結する仕組み（分母の確保）
2. 1〜3 体目の指示を、拾える範囲で同じ形に落とす（事故の分だけでも）
3. 条件は**変えない**。変えたくなったら、変える理由を先に書いてから変える

★ 表記の注意: `N 件中` の形は**測定の検体数**の印として番人が見張っている（tests/test_battery_number_is_current.py）。断りの件数のように無関係な分母は`N 件のうち` と書く ── 例外簿に足して番人を緩めない（2026-09-17 に 1 度踏んだ）。
