## 2. 各失敗ケースの機構分析（行番号は測定時点の `ailine.py`）

### A — 見出しは常に物理1行目という前提（title_rows.xlsx）
- `book_columns()`（254-269行）: 「全シートの見出し行（1行目の値）」を機械的に読む。実際の見出しが何行目にあるかは一切考慮しない。
- `describe_book()`（236-251行）も同様に「行0(見出し)」固定。
- 今回は 1行目が結合タイトルセルで他列が `None` のため `book_columns` の列挙ループ（264-267行, `if v in (None, ""): break`）が1列で止まり、`resolve_col_ref()`（882-895行）が「金額」を解決できずエラー文を返した。
- `verify_dsl_args` の SORT 分岐（925-929行）→ `cmd_run_dsl`（2024-2027行）が `ok=False` を「？ {err}」として出力し即 exit 3。★ この経路自体は健全（推測で断定せず止まる）。ただし前提（見出し=物理1行目）が崩れる帳票では、たまたま「実在しない列名」として弾かれたから安全に止まっただけで、もし1行目にたまたま実在しそうな列名（例えば別の意味で「金額」という語）が入っていたら誤接地したまま静かに進んだ可能性がある（未検証・推測）。

### B — MAX_ROWS=1000 は「診断ログ」の死角であって「適用」の死角ではない（large.xlsx）
- `MAX_ROWS = 1000`（126行）は `snapshot()`（290-326行、特に 299-300行 `nrow = min(ws.max_row or 0, MAX_ROWS)`）にのみ効く。
- 実際の並べ替え適用は LibreOffice の UNO 経由（`SortByColumn` ヘルパ、`helpers/AiLineHelpers.bas` 14-49行）で行われ、Python 側の MAX_ROWS とは無関係に全データ範囲に効く（実測: 3,000行とも正しく降順）。
- SORT の事後条件 `check_sort()`（1240-1257行）は `openpyxl.load_workbook(path)` を直接開き `_scan_last_row()`（1210-1215行）で最終行を求めるため、これも MAX_ROWS の制限を受けない（全行検証）。
- 一方、`diff_snapshots()`（364行〜）が生成する「変更点」ログと `build_advisories()`（658-675行、幽霊データ検出・一様埋め検出・件数突き合わせ・依頼文言との重なりチェック）は全部 `snapshot()` の出力（MAX_ROWS切り詰め済み）を材料にしている。今回の実測で、真の変化8,961セルのうち1,000行境界を超えた5,985セル（67%）が「変更点」ログにも advisories の計算対象にも一切現れないことを確認した。
- ★ リスクの所在: 今回の SORT のように op 別の全行事後条件 (`run_postcondition`) がある操作は結果自体は正しく検証される。しかし **事後条件を持たない FREEFORM 経路**（`cmd_run_freeform`, 2125行〜）は no-op ガードも M2a advisories も全部 `snapshot()` 頼みなので、1,000行を超える帳票で変化が1,000行目以降に集中した場合、理論上「実際は変わっているのに no-op と誤判定される」「幽霊データ等の advisories が発火しない」死角になり得る（★ 本 battery では直接は再現していない・B の SORT は専用の全行 postcondition があったため露呈しなかった。FREEFORM×大規模帳票の組み合わせは未測定）。

### C① — no-op ガードは「依頼どおり何もしない」と「失敗して何もできなかった」を区別できない（formulas.xlsx）
- no-op 判定・修復トリガーは `cmd_run_freeform` 内 2211行 `print("× no-op（実行は成功したが文書に変化が無い）。修復する。")`。
- この判定は「変化の有無」のみを見ており、依頼文の意味（「何もしないでください」）を一切考慮しない。★ 設計思想（README 82-86行の no-op ガード説明）は「LLM が実行時エラー無しで成功と報告し実際は何もしない」ことへの対抗だが、依頼自体が「何もしない」ことを求めるケースは想定されていない。
- TODAY() の揮発性による偽陽性は、before/after のスナップショットが同日中に取得されるため（`normalize_book` でLibreOfficeが開き直す際に再計算されるが、日付が変わらない限り値は不変）今回は発生しなかった。日付を跨ぐ実行（深夜0時前後）でのみ理論上再現しうるが、本 battery では未確認。

### C② — `_scan_last_row` の「列A走査」は合計/フッタ行をデータ行と誤認し、事後条件が None 比較でクラッシュする（formulas.xlsx）
- `_scan_last_row(ws, key_col=1)`（1210-1215行）は列A（key_col既定=1）が空になるまでの行を「データ行」とみなす。formulas.xlsx の7行目「合計」は列Aに値があるため対象に含まれてしまう。
- `check_sort()`（1247-1248行）: `last = _scan_last_row(ws)` → `vals = [ws.cell(row=r, column=idx).value for r in range(2, last + 1)]`。7行目のB列（数量）は空欄=`None` のままリストに入る。
- 1253-1254行 `all(vals[i] >= vals[i + 1] ...)` が `None` と `int` を比較して `TypeError` を送出。ここには try/except が無く、そのまま `cmd_run_dsl`（2094行の呼び出し元）経由で `main()` まで伝播し `raise SystemExit(main())` の外側で未捕捉の生トレースバックとして表示される。
- 実際の並べ替え適用自体（`SortByColumn` ヘルパ、helpers/AiLineHelpers.bas 14-49行）は「合計」行を範囲に含めていても、LibreOffice のソートは空欄セルを昇順/降順に関わらず末尾に置く挙動のため、たまたま元の位置（最終行）に留まり、D列の数式も UNO ネイティブソートの相対参照追従によって壊れずに残った（実測で確認）。★ つまり「合計行の混入」自体は今回は実害を生まなかったが、ailine 自身の検証コードがその混入に耐えられず落ちた。

### D — 2段見出し＋結合セルで、列の接地情報が根本から欠落し、ヘルパの「データ行検出」も巻き添えで沈黙する（merged_head.xlsx）★ 最重要
- 接地の欠落: `book_columns()`（254-269行）は物理1行目のみを見出しとして読み、`headers.get(sheet)` として `["商品", "上期"]` を返す（`下期` は B1:C1, D1:E1 の結合により C1 が `None` になり、264-267行のループが `break` して打ち切られるため列挙に到達しない）。実データの月名（2行目）は一切、翻訳 LLM にも `verify_dsl_args` にも渡らない。
- 誤接地の通過: LLM は与えられた語彙 `["商品","上期"]` の中から「7月」に対して「上期」を返した（推測）。`resolve_col_ref()`（882-895行）は実在列名なので `s in headers` が真になり、誤りなく通過（886-888行）。`verify_dsl_args` の SORT 分岐（925-929行）はここでは何も検出できない — 「実在するか」だけを見ており「依頼の趣旨と合っているか」は見ていない。
- codegen: `codegen_dsl`（1070行〜、SORT の該当箇所 `headers[first_sheet].index(resolved_args["col"])`）が `"上期"` のインデックス(=1、0起点で列B)を渡し `SortByColumn(oDoc, 1, False)` を生成。列Bは実データでは「4月」の値であり、ユーザーが意図した「7月」列（D列）ではない。
- ヘルパ側の沈黙: `SortByColumn`（helpers/AiLineHelpers.bas 14-49行）はデータ範囲を「列0(A列)を上から走査」で決めるが（19-24行）、2行目（月名行）のA列が空文字のため `lastRow` が1のまま `lastRow = lastRow - 1` で 0 になり、33行 `If lastRow < 1 Then Exit Sub` により**何もせず終了**。
- 検証の沈黙: `diff_snapshots` は差分ゼロ、`check_sort()` の 1250-1251行 `if len(vals) < 2: return True, "行数が少なく比較不要"` が「データが無い」ケースと「本当に1行しかない」ケースを区別せず `True` を返す。`cmd_run_dsl`（2094-2104行）はこれを素直に「postcondition pass」として `✓ 達成を機械検証済み` を出し `ok=True`、exit 0 で終わる。
- ★ 3つの独立した層（接地・codegen・事後条件）が、それぞれ別の理由でこの帳票の構造（2段見出し＋結合＋その下の空セル）を「データが無い」と解釈し、結果として全部が沈黙で一致してしまった。どの層も単独では「怪しい」と気づけるチェックを持っていない。

## 3. 所見の要約

### 「静かに壊れる」型（最悪 — 見た目 ✓ だが実は違う/何もしていない）
- **D（merged_head.xlsx, 7月で降順）**: 唯一・かつ最も重大なケース。`ok=True`・`postcondition=pass`・「✓ 達成を機械検証済み」を表示しながら、実際は原本と1バイトも変わらない完全な no-op。しかも確認行に表示される対象列名（「上期」）自体がユーザーの依頼（「7月」）と食い違っており、その食い違いを指摘する advisories も一切出ない。DSL 経路（`cmd_run_dsl`）には FREEFORM 経路にある no-op ガード（2211行）に相当する「変化が無ければ失敗」というチェックが存在せず、op 別事後条件（`run_postcondition`）だけに検証を委ねているため、その事後条件自身が「データ0件」を「合格」として素通しする設計（1250-1251行）だと、この二重の穴が重なって静かに壊れる。

### 「正直に失敗する」型（許容 — エラーで止まる・CLARIFY・トレースバックで気づける）
- **A（title_rows.xlsx, 金額で降順）**: 実在しない列名として即座に「？」で止まる。安全側。
- **B（large.xlsx）は「正しく動いた」に分類**したが、人間向けログの死角（真の変化の67%が非表示）は別軸の誠実さの問題として記録した。
- **C①（formulas.xlsx, 何もしないでください）**: no-op ガードが「意図的な no-op」を「失敗」と誤分類するが、少なくとも `ok=False` で誠実に「達成できなかった」と報告しており、ユーザーを騙してはいない（不便だが安全）。
- **C②（formulas.xlsx, 数量で降順）**: 生の Python トレースバックが出るのは見苦しいが、`ok=True` を騙る余地はなく exit 1 で確実に「何か変」だとユーザーに伝わる。実際の並べ替え適用自体は正しかった点は皮肉。

### 全体としての一言
5ケース中4ケースは「壊れるにせよ、壊れたと分かる」形で失敗した。唯一 D だけが、2段見出し・結合セルという実務帳票にありふれた構造の下で、ailine の3つの検証層（接地・codegen・事後条件）が同じ理由で同時に沈黙し、「確認済み」という最も強い言葉で完全な no-op を報告した。★ MAX_ROWS=1000 の死角（B で定量化: 実変化8,961セル中5,985セルが人間向けログから消える）は、今回計測した5ケースの中では実害を生まなかった（SORT に専用の全行事後条件があったため）が、事後条件を持たない FREEFORM 経路×1,000行超の帳票という組み合わせでは同種の死角が実害化しうる、と推測される（未測定）。
