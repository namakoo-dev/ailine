# 検体: 受け取った請求書 40 冊（骨は実物・肉は合成）

2026-09-10。需要①「請求書 40 ファイルからの抜き出し」を、**実物の構造の上で・答え付きで**
測るための検体。3 人の設計者が独立に「これを最初に作れ」と言ったもの。

## なぜこの形か

同じ需要を 3 通りの検体で測って、3 回とも別の理由で外した:

```
① 合成 40 冊（bench/folder_map/）   構造が想像だった
     実物は「表」でなく**帳票**。取引先は列でなくセルに在り、明細の和は小計（税抜）で
     請求額ではなかった。合成に合わせて作ると全件が消費税ぶん少ない数字を静かに出す
② 実物の雛形 22 冊                  **答えを持たなかった**
     中身が伏せ字（〇〇 〇〇）なので「取れた」は数えられても「正しい」が言えない。
     実際に宛先を 15/16 で誤って取り、それを「15/15 成功」と報告した
③ この検体の初版                    答えを**成果物でなく想定から**作った
     雛形に見本の明細が入っていることを見落とし、40/40 で外した
```

→ **骨は実物の雛形をそのまま使い、肉（値）だけ流し込む。** 答えは流し込んだ側が持ち、
**成果物と突き合わせて 40/40 で一致することを確認してから採用する**（`mk_received.py` の受け入れ条件）。

## 使い方

雛形は他社の著作物なので **この repo には含めない**。各自で入手して隣に置く。

```
bench/received_invoices/
    mk_received.py        ← 検体を作る（このファイル群は追跡される）
    score_designB.py      ← 採点する
    real14/               ← ★ 各自で用意（Misoca/弥生 の雛形）
    construction_bill.xlsx  ★ 各自で用意（マネーフォワード）
    inv21.xlsx              ★ 各自で用意（マネーフォワード・別レイアウト）
    received40/           ← 生成物（追跡しない）
    答え_received40.json  ← 生成物（追跡しない）
```

```
python mk_received.py     # 40 冊を作り、LibreOffice で開き直してキャッシュを入れる
python score_designB.py   # 答えと突き合わせて採点する
```

★ `SKELETONS` の番地（`issuer` / `atesaki` / `detail`）は雛形ごとに手で確かめた値。
別の雛形を足すなら、**その雛形を開いて番地を目で確かめてから**足すこと。

## ★ 検体を作って初めて出た、実物の知識

読むだけでは出ず、**書いてみて出た**もの。どちらも抽出の設計に直接効く。

**① 明細行の存在は「品名」でなく取引日で決まる骨がある**

```
inv21:  K33 = IF(B33="","", H33*I33)      ← B は取引日
        品名・数量・単価を入れても、取引日が空だと金額が出ない
```

**② 集計は税率区分ごとの SUMIF（軽減税率対応）** ── ただし素朴な検算は誤報しない

```
inv21:  D51 = SUMIF(J33:J48, 10%, K33:K48)     ← 10% 対象だけ
        D52 = SUMIF(J33:J48,  8%, K33:K48)     ← 8% 対象（軽減税率）
        C51 = ROUND(D51*10%, 1)   C52 = ROUND(D52*8%, 1)
        消費税セル K50 = C51 + C52               ← ★ 区分ごとに丸めた**合計**が既に入っている
```

★ 予想 →実測 →再反証まで 3 段で動いた。**この項目の記録は 3 回書き換わっている**:

```
1  予想   「区分ごとに丸めるから 明細の和 + 消費税 では合わない」（未測定の当てずっぽう）
2  実測   inv21 骨で 8% を 1 行混ぜたら 50,000 + 4,680 = 54,680 = 合計 で**閉じた**
           → 消費税セル K50 が区分ごとの丸め済み合計を持っているため
3  ★ 再反証（設計者 A が測定）  **骨によって違う**。construction_bill 骨は
           G26=10%分 / G27=8%分 / G28=合計 で、最初に見つかる『消費税』ラベルが
           **10% 分**なので、正しい冊に「割（食い違い）」が出る ＝ **誤報**
```

★ **「誤報しない」は inv21 骨 1 種でしか確かめていなかった。** 骨ごとに帯の作りが違う。
検算は「帯のラベルを読む」でなく「帯の数値集合に Σ明細 や 差 が在るか（値の目撃）」で
組む方が幾何に依存しない（設計者 A・C が独立に提案）。★ 未実装・未測定。

★ 税率の列（J）を空にすると SUMIF が 1 行も拾わず合計が 0 になる ── 検体を作る側の罠。

**③ 実物の金額はすべて式** ── openpyxl で書いて保存しただけではキャッシュが無く、
`data_only=True` で全部 `None` になる。LibreOffice に開き直させる段が要る
（`mk_received.py` の `recalc()`）。

**④ 結合セルは左上以外に書けない**（`MergedCell` は read-only）。実物の帳票は結合が
43〜174 箇所ある。

## ★★ v2（2026-09-11）── 欠陥は直り、検体は 87 冊になった

v1（`mk_received.py`・40 冊）の既知の欠陥 4 つは **v2（`mk_received_v2.py`・87 冊）で直った**。
★ v2 は**規則を書く者とは別の者が書いた** ── 依頼書に「どんな規則を作るつもりか」を
書かずに渡した。規則を知って検体を作ると、その規則に当たる検体しか出てこないため。

```
群      基礎 36 ／ 税率 6 ／ 敵対 40 ／ 混入 5     骨 12 種（4 ベンダ）
① 交絡  ★ 直った ── 骨 6 種 × 明細行数 {0,1,2,3,5,8} の**総当たり 36 冊・各セル 1 冊**
        （成果物から数えて確認。v1 は骨と行数が同期していた）
② 宛先  ★ 直った ── 「御中のセル == 宛先社名」は **12/36 でしか真でない**
        （真 12 / 偽 12 / 御中なし 12。v1 は作り方によって全部真だった）
③ 敵対  ★ 入った ── 40 冊。うち**陰性対照 6 冊**（割を出したら誤報、を測れる）
④ 軽減  ★ 入った ── 6 冊。骨によって持ち方が 3 通り（記号列 / 税率列 / 単一税率セル）
```

## ★ 採点器 `score_v2.py`（2026-09-11）

```
python bench/received_invoices/score_v2.py --self-test      # ★ 点数を見る前に必ず
```

**測る前に凍結した条件**（あとから緩めない）:

- 分母 = 検体を書いた側が宣言した `期待` の件数（171）。★「取れた数」を分母にしない
- 正 = 区分が許された組に入る ＋ 値が一致 ＋ 禁止値でない ＋
  空欄なら理由が `名指し` の語をすべて含む
- 見出しにするのは正答率ではなく **誤報**（値を出して間違えた）の数

★ この採点器は `ailine_core.field_record` を **import しない**。
区分の意味・値の同一性・丸めを別に書き直している ──
2026-09-10 に、採点器そのものが結合セルの写しを 2 つ目の根拠として数え、
40 冊すべてを「確」と報告した（畳むと 確 14 / 単 26）。
**同じ関数で作った分母は分母ではなく感想**。

`--self-test` は対照 2（答えをそのまま返す／何も返さない）と変異 3 を通す。
変異の期待値は「> 0 なら合格」ではなく**答えから算術で出した正確な件数**で見る。
群を絞ると当てる対象が無い変異が出るが、そこは
**「効かなかった」ではなく「測れなかった」**と分けて報告する。

★ 実際、この採点器自身に欠陥が 2 つあり、どちらも変異で出た ──
理由が空の空欄を 134 件「安全」と呼んでいた／
正解値を指定しない冊（`値: None`）で**正しい抽出を誤報と呼ぶ**ところだった。
